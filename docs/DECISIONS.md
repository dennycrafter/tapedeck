# Decisions

This file records every deviation from SPEC.md and every choice the spec left open, one entry at a time (SPEC section 0, rule 2). Nothing in the app is invented silently: if a judgement call was made during the build, it is written down here.

Each entry lists the date, the ticket, the decision, and a one line reason for it, newest first. Entries are never edited after the fact; a later decision that replaces an earlier one is added as a new entry that names the entry it replaces.

## v2 (T9 to T14, see docs/build/V2-PLAN.md)

Each v2 ticket adds its entries under its own heading below, newest first, so tickets built at the same time never edit the same lines.

### Plan
- 2026-10-15 (v2 plan): Friends who want Tapedeck each run their own copy (own Vercel, Supabase, R2 and PC downloader); there is no shared multi-user server. Reason: a shared server would store downloaded songs and stream them to other people, which is distributing copies, not personal use.
- 2026-10-15 (v2 plan): Trim is stored as start and end points; the audio file is never cut. Reason: undo must always work and the offline copy stays the same file.
- 2026-10-15 (v2 plan): Catalog search uses Deezer's free public API with iTunes as the fallback, not Spotify. Reason: since February 2026 Spotify's API needs the app owner to pay for Premium, allows 5 users, caps search at 10 results and only returns tracks of playlists you own.
- 2026-10-15 (v2 plan): Import offers a MusicAPI.com login and paste-a-link. Reason: our own Spotify login would be limited to 5 people and Spotify only lifts that for businesses with 250,000 monthly users; Denis wants a playlist checklist, not one link at a time.
- 2026-10-15 (v2 plan): The best-copy finder only uses freely available sources (YouTube Music, SoundCloud, YouTube) and never tools that strip DRM from paid streaming services. Reason: breaking copy protection is a line Tapedeck does not cross.
- 2026-10-15 (v2 plan): Speed uses the audio element's playbackRate and preservesPitch; pitch shift without a speed change is out of scope. Reason: it needs Web Audio, which stops when the iPhone locks.

### T9
- 2026-10-15 (T9): `e2e/prod-server.mjs` starts `npx.cmd` through a shell on Windows. Reason: recent Node versions refuse to start `.cmd` files without one (`spawnSync npx.cmd EINVAL`), so the e2e checks could not run on a Windows PC; Linux and CI are unchanged.
- 2026-10-15 (T9): Windows-only test failures that also fail on main and pass on CI (Linux): `split-sql.test.ts` schema copy (CRLF line endings), `storage.test.ts` nested key path (backslashes), and two `test_apple_music.py` iTunes prefs tests (Windows paths). Left alone; CI is the judge. Reason: they are not caused by v2 and fixing them is outside T9.
- 2026-10-15 (T9): The `e2e:tN` scripts match whole tags (`@T(0|1|...|N)(?![0-9])`) instead of `@T0|@T1|...`. Replaces the T0 to T8 pattern. Reason: `@T1` would also match `@T10` to `@T14`, so `e2e:t10` would have run T11 to T14 tests.
- 2026-10-15 (T9): The e2e production build goes into `.next-e2e-<port>` and builds with a git-ignored copy of the tsconfig (`tsconfig.e2e-<port>.json`, picked through `TAPEDECK_TSCONFIG` in next.config.ts). Reason: Next.js adds every build folder's type paths to the tsconfig it builds with; with the real one, each worktree's port would leave a change in `tsconfig.json`.
- 2026-10-15 (T9): The player's track (`PlayerTrack`) and `toPlayerTrack` already carry the trim and speed fields, optional. Reason: T10 and T14 both need them; adding them once here keeps those two tickets from editing the same lines.
- 2026-10-15 (T9): Claim also returns `resolved_url` (the plan lists it under T12). Reason: the column exists from T9, and returning it now keeps T12 out of the claim query, a shared hot spot.
- 2026-10-15 (T9): Invalid optional v2 fields on `complete` and `fail` answer 400 and store nothing, like the existing fields. The auto trim is checked against `durationSec` from the same call, or the stored length when it is left out, with half a second of slack (the stored length is rounded). Reason: one rule for every field, and a bad suggestion never half-lands.
- 2026-10-15 (T9): After applying migrations the runner re-runs the RLS rule from the end of schema.sql (RLS on for every public table, grant to service_role on Supabase). Reason: a table a migration creates gets the same protection without each file repeating the block.
- 2026-10-15 (T9): Migrations run statement by statement (the schema splitter) inside one transaction per file, under a transaction-scoped advisory lock, and the runner re-checks `schema_migrations` after taking the lock. Reason: postgres.js's extended protocol rejects multi-statement strings, and two Vercel instances starting at once must not run a file twice.
- 2026-10-15 (T9): Migration files are embedded in `web/lib/migrations-sql.ts`, generated by `npm run gen:migrations` (scripts/gen-migrations.mjs); a test fails when it drifts from `supabase/migrations`. Reason: the folder is outside the `web` root Vercel builds, the same reason schema.sql is embedded in schema-sql.ts. When two tickets both add a migration, resolve a conflict in this file by rerunning the generator.
- 2026-10-15 (T9): On the real database, pending migrations run on first use only when the `settings` table exists; before setup they are skipped and Finish setup applies them right after schema.sql. A failing migration fails that first use (and is retried on the next one). Reason: the Setup page must keep working on an empty database, and running on a half-migrated schema would fail in less clear ways.

### T10
- 2026-10-15 (T10): No waveform in the trim editor. Reason: the plan marks it optional, and doing it right means computing it on the PC and a new column; the handles, fields and the two previews cover the job.
- 2026-10-15 (T10): The copy in Apple Music's auto-add folder is the whole, untrimmed file. Reason: trim is non-destructive and Apple Music cannot read Tapedeck's start and end points.
- 2026-10-15 (T10): The trim end is noticed on `timeupdate`, so a song can run up to about a quarter of a second past it. If the next song's link was not prefetched, the old file keeps playing until the new one arrives instead of being paused. Reason: `timeupdate` is the only signal that keeps working with the iPhone locked, and pausing then playing again from a network callback risks the iPhone refusing to play.
- 2026-10-15 (T10): Trim changes are saved with the Edit details Save button, together with the other fields, not instantly. Reason: one Save keeps the dialog simple, and Cancel then really cancels.
- 2026-10-15 (T10): "Play from start" and "Hear the ending" play the song through the main player as a queue of just that song, with the trim not yet saved; the previous queue is not restored afterwards. Reason: restoring the old queue and position needs new player plumbing (watching for the preview to end), which is not simple; a preview acts like tapping the song.
- 2026-10-15 (T10): `PATCH /api/tracks/:id` checks the trim that would result (hand value, else the PC's suggestion, else the whole song), and allows the end up to half a second past the stored length. Reason: the stored length is whole seconds while the PC's suggestion may sit a fraction past it (same allowance as `/api/agent/complete`); checking only the sent values would let a hand start pass that leaves less than 10 seconds before a suggested end.
- 2026-10-15 (T10): The player store keeps `position`, `duration`, seeks and the saved position in trimmed time (0 at the trim start). An end at or past the stored length plays to the file's own end, and a range under one second is ignored (the whole song plays). Reason: the scrubber, the clocks and the lock screen then need no changes; saves from before T10 had no trims, so they mean the same; "Don't trim" never cuts the last fraction of a second, and bad data never skips a song.
- 2026-10-15 (T10): silencedetect counts a silence as "from 0" when it starts within 0.05 s of 0, and as "to the end" when it has no `silence_end` or one within 0.25 s of the end. Reason: the ffmpeg 9 build on this PC prints a last `silence_end` at the end of the file, and older builds may print none; both must work.
- 2026-10-15 (T10): SponsorBlock is asked about `resolved_url` (the copy the PC picked, T12) when set, else `source_url`. `--selftest` runs the silence check only and never calls SponsorBlock. Reason: catalog songs have no YouTube link of their own; T12 can put its pick in `resolved_url` on the claimed row. The e2e checks run `--selftest` and must not use the network.
- 2026-10-15 (T10): SponsorBlock segments in the middle of a song are ignored; only one that starts within 1 s of 0 or ends within 1 s of the end becomes a trim. Reason: the plan; cutting from the middle would need the player to skip, which is out of scope for now.

### T11
- 2026-10-15 (T11): 30 second previews are not built (the plan makes them optional). Reason: they need the one audio element (SPEC 8.8) to be borrowed and given back, and Deezer's preview links are signed and expire within hours, so they cannot be cached for 24 hours with the rest; better as a small follow-up if Denis wants them.
- 2026-10-15 (T11): The catalog stand-in answers from `web/e2e/fixtures/catalog-deezer.json` and `catalog-itunes.json` whenever `TAPEDECK_TEST=1`; `CATALOG_SOURCE=fixtures` turns it on for offline development (ignored by a real production build) and `CATALOG_SOURCE=live` turns it off (unit tests use that to test the real code path against MSW). The switch is not in `.env.example`. Reason: the e2e server makes real network calls (MSW only runs inside unit tests), so the stand-in has to live in the app, like the other 4.1 stand-ins; the owner never needs the switch.
- 2026-10-15 (T11): The recorded fixtures keep Deezer's and iTunes' bodies as returned, except that Deezer preview links (`hmac=`) and `track_token` values are replaced with `fixture`, and the files are written with `\uXXXX` escapes for non-ASCII text. Reason: `check-repo.sh` rejects 64-character hex strings and raw en or em dashes (real titles contain them), and the signed values expire anyway.
- 2026-10-15 (T11): Deezer sends errors as HTTP 200 bodies with an `error` object: code 800 ("no data") means the album or artist does not exist (404 in the routes), any other code counts as Deezer being down. Reason: that is what the live API returned on the record date.
- 2026-10-15 (T11): The iTunes fallback works per search call (songs, albums and artists each fall back on their own). Album and artist pages stay with the provider their id names (`deezer:` or `itunes:`); when Deezer is down a `deezer:` page shows "The music catalog is not answering. Try again in a moment." Reason: the two catalogs' ids do not translate into each other.
- 2026-10-15 (T11): Fallback (iTunes) answers are cached for 24 hours like Deezer ones. Reason: one rule, and iTunes allows only about 20 calls a minute.
- 2026-10-15 (T11): An album page asks Deezer for `/album/:id` plus `/album/:id/tracks?limit=200`; an artist page for `/artist/:id`, `/artist/:id/top?limit=10` and `/artist/:id/albums?limit=100`. Search asks for 25 songs, 25 albums and 10 artists. Reason: the tracks list carries the ISRC, track and disc numbers, which the album's own embedded list lacks, and it is not cut short on long albums.
- 2026-10-15 (T11): Adding refuses a song as "Already in your library" only for the same catalog id, the same ISRC, or a repeat in the same request. A same-title match (8.5 rules) only sets the "In library" flag, which hides the Add button and makes Add album skip the song. Reason: the 8.5 normaliser drops brackets, so a remix or live version matches the original; the server should never refuse on a guess.
- 2026-10-15 (T11): A Deezer song sent without an ISRC (artist top lists have none) gets it from `/track/:id` while adding, 5 at a time, at most 6 seconds in total; without it the song is added anyway. Reason: T12 and the ISRC duplicate check use it, and an add must stay fast.
- 2026-10-15 (T11): "In library" for an album means an album with the same normalised name by a matching artist is in the library (on the album page: every song is). For an artist it means the exact normalised name. Reason: the plan defines the flag for songs only; "contains" for artists would also flag "Daft Punk - Stardust".
- 2026-10-15 (T11): Catalog search needs 2 characters (like YouTube search) and the page always asks for all three kinds; the tabs show parts of that one answer. Reason: switching tabs is instant, and 3 Deezer calls per pause in typing stay far below Deezer's 50 calls per 5 seconds.
- 2026-10-15 (T11): Library matches show at the top of the Top tab under "In your library"; the other tabs show catalog results only. The query and tab are kept in the address (replaced, not added to history), so Back from a catalog artist or album page returns to the same results. Reason: "filters your own library on top" without repeating it on every tab.
- 2026-10-15 (T11): Catalog songs store the 600x600 cover; result lists show a 250px thumbnail that is never stored. Reason: the T3 cover rule for stored covers, without loading 25 full-size covers per search on a phone.
- 2026-10-15 (T11): The Search item in the sidebar and the phone tab bar stays highlighted on the catalog artist and album pages (a one-line change in `AppShell.tsx` and `PhoneTabBar.tsx`). Reason: those pages are reached from Search.

### T12
- 2026-10-15 (T12): The finder sets `resolved_url` (as well as `source_url`) on the track it hands to the pipeline, and `upload_track` takes T10's `auto_trim` and T12's `extra` side by side. Reason: T10's trim step asks SponsorBlock about `resolved_url`, so catalog songs get the SponsorBlock trim of the chosen copy, and the two sets of complete fields never share a key.
- 2026-10-15 (T12): The finder fixtures are 14 real songs recorded once on Denis's PC (ytmusicapi 1.12.3, yt-dlp 2026.08.19), trimmed (thumbnails, unused fields and video-only formats dropped, long descriptions cut) and written with JSON `\u` escapes. Reason: the raw `yt-dlp -J` output is up to 600 KB per video, and real titles contain en and em dashes that check-repo.sh forbids; the escapes keep the data exact.
- 2026-10-15 (T12): The plan's traps map to recorded data as follows: live version (Eagles, 405 s live video against 391 s), sped up edits (Arctic Monkeys on YouTube Music), a video with an intro (the Calvin Harris official video runs 18 s long; its lyric videos 8 s long), and a SoundCloud-only song (a fan edit with a made-up `import:soundcloud:` catalog id, since it has no Deezer entry). The Deezer lookup for Lady Gaga "Bloody Mary" returned a remix filed under the artist "Trinix Remix"; it stays in as a real messy catalog row. Reason: no recorded result was a lyric video exactly 20 s long, and the length check treats 18 s the same way.
- 2026-10-15 (T12): Scoring: title token overlap x 0.5, artist match x 0.3, official upload +0.15, ISRC in the description +0.15, source +0.1 (YouTube Music) / +0.05 (SoundCloud) / 0 (YouTube), up to +0.05 for a close length, -0.3 per version word (at most -0.6), -0.1 when the result has no length. A copy needs 0.7 to be downloaded; 0.95 stops the search early; the top two within 0.05 of each other are a tie. Reason: tuned on the 14 recorded songs so every pick is the album version, with and without YouTube Music.
- 2026-10-15 (T12): More version words than the plan lists: acoustic, a cappella, demo, mix, edit, stripped, flip, bass boosted, loop, and "letra" next to lyrics. Words in the catalog title or the catalog artist do not count. Reason: the real results were full of club mixes, TikTok edits and Spanish lyric videos, and Deezer files some remixes under the remixer as the artist.
- 2026-10-15 (T12): The official bonus needs the artist to match, even for YouTube Music songs and "Topic" uploads; a plain channel counts as official when its name is the artist once "official", "VEVO", "Topic" and spaces are left out. Reason: YouTube Music lists covers by other artists as songs, and with a smaller bonus a SoundCloud re-upload beat Queen's own channel on bitrate.
- 2026-10-15 (T12): A catalog title suffix like " - 2011 Remaster" is ignored when matching titles. Reason: it names the same recording, and YouTube titles rarely carry it.
- 2026-10-15 (T12): `yt-dlp -J` is only run on a near tie, on the top two. The full description it returns also feeds the ISRC bonus; otherwise only SoundCloud search results carry a description. The ISRC never appeared in a recorded description, so the bonus is tested with a made-up one. Reason: the plan keeps the detail lookup to the top two to stay fast.
- 2026-10-15 (T12): YouTube Music copies are stored as `https://www.youtube.com/watch?v=<id>` with source "ytmusic". Reason: it is the same video, and it matches the app's one canonical YouTube link form.
- 2026-10-15 (T12): matchInfo alternatives include copies rejected for their length, with score 0, after the accepted ones. Reason: with no match, a slightly longer video can still be picked by hand.
- 2026-10-15 (T12): "Couldn't find a matching version" goes through the normal `fail`, so the server requeues it while attempts are under 3 and the PC searches up to three times before the song shows as failed. A failed download of the chosen copy also sends matchInfo. Reason: keeps `/api/agent/fail` (a shared hot spot) unchanged, and the alternatives are saved either way.
- 2026-10-15 (T12): The downloader skips the search whenever a claimed catalog row has `resolved_url`, and then sends only `resolvedUrl` on complete (the stored matchInfo stays). Reason: the only other writer of `resolved_url` is complete, on ready rows, and a ready row comes back to the queue only to be fetched again (for example "Add to Apple Music"), where the same copy is right.
- 2026-10-15 (T12): When the chosen SoundCloud copy is DRM protected, the existing YouTube fallback downloads it, and `resolvedUrl` still names the SoundCloud link. Reason: the fallback does not report which video it took; changing that means reworking `download_track`, which T10 is editing at the same time.
- 2026-10-15 (T12): "Search again" is `POST /api/tracks/:id/pick { searchAgain: true }` (clears `resolved_url`); `{ url }` picks a copy. Both set `waiting`, attempts 0 and no error, and keep `match_info`. A saved candidate's url is stored as is, a pasted link in its canonical form, and a song the PC is downloading answers 409. Reason: the plan names only `{ url }`; one route keeps both actions in one place, and the alternatives stay visible while the song waits.
- 2026-10-15 (T12): The pick logic is split into `web/lib/pick-version.ts` (pure, used by the dialog) and `web/lib/pick-version-db.ts` (the update). Reason: the dialog must not pull the database driver into the browser bundle.
- 2026-10-15 (T12): The e2e checks seed catalog songs through a new test-only route, `/api/test/seed-catalog` (same TAPEDECK_TEST switch as `/api/test/seed`). Reason: T11's catalog adding is built at the same time, and editing the existing seed route would collide with other tickets.

### T14
- 2026-10-16 (T14): Plan item 4 answer: on CI's WebKit (Playwright iphone project, Linux), a song at 1.25x with the pitch off followed by one at 0.85x with the pitch off keeps the second song's `playbackRate`, `defaultPlaybackRate` and `preservesPitch = false` after the new `src` loads and plays, and after a pause and play; it measurably plays slower. The next song at normal speed goes back to 1x with the pitch kept. Reason: recorded so the real-iPhone check in the handoff list only has to confirm the locked screen.
- 2026-10-15 (T14): The player store keeps `position`, `duration` and seeks in media time (the file's own seconds, trimmed as in T10); the player bar and Now Playing divide them by the song's speed, and the scrubber converts back when seeking. Reason: trim, saved positions, the lock screen's `seekto` and the 30 second rule all stay in one clock, and only two display spots change.
- 2026-10-15 (T14): The lock screen gets media time plus `playbackRate` in `setPositionState`, so it shows the song's normal length (3:00) and runs its clock 1.25 times as fast, ending with the song; the app shows 2:24. Reason: the plan asks for the rate there, and that is how the Media Session API defines it (Apple's own players do the same at other speeds).
- 2026-10-15 (T14): Song lists keep showing the file's own length, with the speed as muted text ("1.25x") next to it for songs not at normal speed; Edit details says "Plays in 2:24 instead of 3:00" (using the trim). Reason: lists already show the untrimmed length since T10, and the same song should show the same length in every list; the speed text says it plays differently.
- 2026-10-15 (T14): At every track start the player sets `defaultPlaybackRate` as well as `playbackRate`, `preservesPitch` and `webkitPreservesPitch` (where present), right after the new `src`, and sets them again on `loadedmetadata` and on every `play`. Reason: loading a new `src` resets `playbackRate` to `defaultPlaybackRate` (HTML media load rules), so a stale default would undo the speed; setting them again covers engines that reset anyway, for example after a lock screen pause and play.
- 2026-10-15 (T14): The 30 second play rule still counts the file's seconds, so a song at 0.5x counts after 60 real seconds and at 1.5x after 20. Reason: the plan (T10) keeps the rule unchanged, and the listened time sent with each play stays comparable between songs.
- 2026-10-15 (T14): The T2 check "30 seconds of listening records one play" now sets its song to 1.5x through `PATCH /api/tracks/:id` instead of forcing the element to 4x, with a 45 s wait and a 90 s test limit. Reason: the player now puts every song's own speed on the element, which overrides a rate forced from the test.
- 2026-10-15 (T14): The Now Playing chip saves a preset or the pitch switch right away and the playing song changes as soon as the server confirms; Edit details saves speed with its Save button, like trim. Reason: the chip is a quick control; in the dialog Cancel must still cancel everything.
- 2026-10-15 (T14): The Speed section shows for every song in Edit details, not only ready ones. Reason: speed needs no length, so a song still waiting for the PC can get its speed ahead of time.
- 2026-10-15 (T14): "Play from start" and "Hear the ending" in the trim editor play at the song's saved speed, not the unsaved one in the dialog. Reason: keeps `TrimEditor.tsx` (T10) untouched.

## v1 (T0 to T8)

- 2026-10-14 (T4 fix): Downloaded songs play from `/offline-audio/<track id>`, an address the service worker answers from IndexedDB with byte ranges (200, 206 or 416); a blob URL (`URL.createObjectURL`, as SPEC 8.9 says) is now only the fallback when no service worker is in control. Replaces the blob-only playback. Reason: in CI, WebKit failed blob playback now and then even as `audio/x-m4a`, while plain addresses played every time; media players stream normal addresses most reliably.
- 2026-10-14 (T7): `scripts/check-repo.sh` leaves out SPEC.md (the build spec, kept exactly as written) and `web/AGENTS.md` (Next.js regenerates it with its own dashes) from the dash check, and SPEC.md and `.env.example` files from the key-prefix check (they only describe the formats). It matches bytes with `LC_ALL=C` so the result does not depend on the machine's locale. It also runs in CI.
- 2026-10-14 (T7): The throwaway e2e secrets are derived at run time (SHA-256 of fixed labels) instead of written as 64-character hex literals; fake keys in unit tests no longer use real key prefixes; the expired CDN signatures in the recorded Deezer fixture are replaced with `redacted`. Reason: the T7 check forbids those strings in tracked files.
- 2026-10-14 (T7): Every en and em dash in tracked files (except SPEC.md) was rewritten; where the character itself matters (the title cleaner's dash separators and their tests) the code uses `\u2013` / `\u2014` escapes, so behaviour is unchanged. Older entries in this file, TEST-REPORT.md and BLOCKERS.md were edited for this only.
- 2026-10-14 (T5): Screenshots are saved as JPEG (quality 82) at device scale 2 on the phone. Reason: 34 PNGs would add about 10 MB to the repo for no visible gain.
- 2026-10-14 (T5): Lighthouse runs inside Playwright (`web/e2e/t5-lighthouse.spec.ts`) with Playwright's Chromium and the session cookie, against the production e2e server. Reason: the pages are behind the password and served with the run's self-signed certificate; running it as a test also puts it in CI.
- 2026-10-14 (T5): The UI checks run with the service worker on (as real users have it). Reason: with it blocked, the service worker helper itself logs an error on every page.
- 2026-10-14 (T4 fix): Downloaded songs are handed to the player as blobs labelled `audio/x-m4a` (Apple's type for .m4a), not `audio/mp4`; Save to Files still builds an `audio/mp4` File as SPEC 8.10 says. Reason: a probe on GitHub's WebKit showed `audio/mp4` blobs failing with "not supported" on some machines while `audio/x-m4a` played every time.
- 2026-10-14 (T4 fix): The service worker no longer uses navigation preload. Reason: offline, a page sometimes opened with the previous page's content; pages are small and the network-first rule is enough.
- 2026-10-14 (T6): "Add to Apple Music" shows in the song menu until the song is flagged (ready, waiting or downloading songs; not failed ones). Flagging a ready song also resets its attempts to 0 when it goes back to `waiting`. Reason: SPEC 8.11 sends ready songs back to the queue; a reset counter keeps the retry ladder fair for this second pass.
- 2026-10-14 (T6): The setting lives at `PUT /api/settings/apple-music { on }` and the song action at `POST /api/tracks/:id/apple-music`. Reason: SPEC 8.11 names the behaviour, not the routes.
- 2026-10-14 (T4): The downloader puts the MP4 index (moov) before the audio in every song: `-movflags +faststart` when converting, and a lossless `ffmpeg -c copy -movflags +faststart` rewrite when a downloaded .m4a has it at the end (kept as is if ffmpeg is missing). The two committed test tones were rewritten the same way (same audio, boxes reordered). Reason: a downloaded copy played from the phone (SPEC 8.9) must read the index first; with it at the end WebKit sometimes never started the song.
- 2026-10-14 (T4): Every play of a downloaded song gets a fresh blob URL (the player no longer caches blob URLs), and the server stores a play sent twice with the same `playedAt` once. Reason: a retry after an audio error must not reuse the same link, and an offline play may be resent after a send that did arrive.
- 2026-10-14 (T4): The offline checks run against a second e2e server, a real production build (`web/e2e/prod-server.mjs`, built into `.next-e2e`, served over https on port 3102) on the same stand-ins. Reason: `next dev` does not run the service worker, and with the network off it will not start the app from cached files even when they are all cached; only a production build shows what the phone will really do.
- 2026-10-14 (T4): `TAPEDECK_TEST=1` now also turns on the local storage stand-in, skips setup mode and enables `/api/test/seed` in a production build. Reason: the e2e production server needs the stand-ins; `db.ts` and the session code already honored the switch in production, so it stays one switch. It is never set on Vercel.
- 2026-10-14 (T4): The service worker has its own caching rules instead of `@serwist/next`'s `defaultCache`: `/api/*` and audio are network only, pages network first, app files and fonts stale-while-revalidate, cover images kept. Reason: `defaultCache` caches `/api/*` responses (SPEC 8.9 says network only) and caches nothing in development.
- 2026-10-14 (T4): Page HTML is not precached, only app code, styles, icons, fonts and the `/~offline` page; pages are cached as you open them. Reason: every page is behind the password, and a page fetched while the service worker installs was stored as the login screen (the offline Home showed the password box).
- 2026-10-14 (T4): Offline plays are queued in a third IndexedDB store, `plays`, and sent with their real time (`playedAt`) when back online; the database is version 2 (the /test-audio page's database had only `audio`). Reason: SPEC 8.6 asks for an IndexedDB queue without naming the store.
- 2026-10-14 (T4): "Save to Files" uses the share sheet only on touch devices (`pointer: coarse`); on a PC it always downloads, even where the browser could share files. Reason: SPEC 8.10 says normal download on PC. When fetching the song takes too long for iPhone's tap-only share sheet, the app keeps the file and asks for one more tap.

Reason: Chromium refuses a service worker served with the run's self-signed certificate, and Playwright can not route requests a service worker makes in WebKit.
